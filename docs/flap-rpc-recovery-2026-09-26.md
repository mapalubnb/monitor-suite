# Flap RPC 停滞修复与验收

日期：2026/9/26（北京时间）。运行版本：Monitor Suite 1.12.7，Flap 1.10.6，Four.meme 1.5.12。

## 故障证据

- 19:18 检查时，合约核心最后成功于 18:28:24，资产最后成功于 18:28:18。Factory、实时提前信号均出现数千块积压。
- 日志主要报本地队列满，而共享预算快照仍有余量。服务器直接读取 Factory 代理槽时，Alchemy、BNB dataseed、Ninicoin、Defibit 均成功，耗时分别为 16、312、335、426 毫秒。这不能解释为四个节点同时不可用。
- Flap 原 RPC 指标停留在 19:05:48，其记录的堆内存约 810 MiB。该旧指标不能用来判断之后的实时错误率。
- 代码只依赖 fetch 的取消来结束网络操作，没有独立的逻辑完成期限。网络操作不结束会继续占用本地槽位，并阻塞等待同一请求的扫描。未获取原进程堆栈，因此不将具体网络库挂起原因表述为已经证实。
- assets、balances 等 RPC 模块复用了外部 API 最长 30 分钟退避，导致底层连接恢复后仍长时间不复核。
- 普通预算等待仅 300 毫秒，低于默认 20 子请求/秒补足 8 项批次所需的约 400 毫秒。在争用时可能尚未补足额度就放弃。

## 实施内容

1. 网络操作增加独立计时器，并向传输层传递取消信号；即便网络 Promise 忽略取消，逻辑调用也结束并释放本地槽位、共享租约。迟到结果不返回扫描逻辑。
2. RPC 指标增加活动槽位数量，独立心跳更新，不再依赖提前信号扫描继续运行。
3. 完整区块缓存同时限制 64 块及 8 MiB 序列化大小，超大区块不缓存；重组校验和实际读取不变。此上限不是进程总堆内存上限。
4. 纯 RPC 模块失败退避上限为 60 秒；启动时对遗留本地队列错误尽快复核，保留错误直到实际查询成功。Safe API、CoW 退避策略不变。
5. 普通预算等待增至 1 秒，Flap 本地排队期限为 3 秒；关键请求仍优先。不提高供应商 RPS、并发额度或监控触发周期。

# 创建者独立补全（1.5.18）

## 本次范围

修复创建者补全依赖历史补扫成功的问题。新增 `creatorDiscovery` 独立 30 秒调度，不改变实时创建者、历史补扫、底池、前端、API、GitHub、OpenFour、合约和链上参数的既有周期。移除历史扫描末尾的重复补全，不清空或推进任何历史游标。

## 流程

1. 从当前静态及指纹目标生成地址集合，对照既有创建者缓存与新核验结果形成缺失清单。
2. 沿用现有开关：启用且有 Key 的浏览器 API 优先（每轮最多 5 地址），网页补充按地址轮转（默认 2 地址），再执行现有有界近期区块反查（默认最多 120 块）。无 Key 不自动启用 API，不绕过网页 403。继承历史补全来源的冷却和扫描进度。
3. 来源给出的是候选，不直接加入观察名单。每轮最多核验两个候选；核对交易 hash、回执状态、区块 hash/高度、目标创建地址、交易与回执发起者，以及区块成员关系。
4. 只有直接创建证据通过后才写入 `snapshot.creatorDiscovery.creators`，下一轮实时/历史扫描自动合入。工厂内部创建因缺 trace 证据保留待办，不把外层交易发送者误认为内部创建者。
5. 候选、失败原因、尝试次数与下次重试时间持久化；暂缺回执保留候选重试，证据不匹配的候选丢弃后重新找来源。任务轮转，不让前两个失败地址长期阻塞其他地址。

所有网络操作在独立工作器完成，最终用短事务发布。其 RPC 使用既有预算器的 `history` 标记，保留核心调用额度与并发余量；不新建高并发查询，不改公共 RPC 限额。独立补全仍会消耗少量既有 RPC 额度，部署后需观察实时扫描延迟。

## 状态与限制

`runtime-metrics.json.creatorDiscovery` 显示本轮时间、监控/缺失数量和每个缺失地址的标签、失败原因、尝试次数、下次重试时间。模块 runs/errorCount 不能代替该逐地址结果。

2026/10/22 修复前只读核验：36 个目标中 11 个缺失；服务器未配置 Etherscan/BscScan API Key，API 开关关闭，网页存在 403；抽查公共 RPC 的两个历史状态请求均报 missing trie node。**用户明确选择暂无可用渠道，先修流程并保留缺失清单。** 因此这次不能保证 11 个地址上线后全部补齐，也不加入未经核验的静态创建者映射。未来由总控安全配置可用来源后继续核验，不在聊天或 Git 中存放凭证。

近期区块反查不是归档全链搜索；已发生很久的创建交易、工厂内部 CREATE/CREATE2 仍可能受阻。新补齐创建者只从现有实时/历史游标参与扫描，不自动为新地址回放已经扫过的历史；如需补齐该段历史，应另行明确范围。

既有创建者缓存保留，未在本次重新追溯核验，覆盖数字区分既有缓存与本次新增验证。没有创建者及手动观察地址时不继续空扫推进游标，等待独立补全建立观察列表。

## 分工存在的具体问题

1. 旧历史覆盖不匹配。48/fast 的 117817600 区块头也返回 null，而不是单纯日志过滤器错误。应记录已测试不可用区间，保留缺口，减少无效重试；不能把整个供应商从近期池封禁。
2. bloXroute 日志不适合当前实时链路。旧历史偶尔成功需要修正此前“缺少可用历史源”的解释：本轮发现可偶发返回旧数据的入口，但仍缺稳定历史服务。它可独立低并发重试旧历史，不能拖住实时或核心状态任务。
3. PublicNode 历史 403 与近期可读取并存。现有 shared/rpc-control.mjs 将 403 统一共享冷却 5 分钟，会把范围受限放大成节点整体不可用。
4. 历史完整区块路由不隔离。flap-monitor/monitor.mjs 的 executeBscRpcRequest 优先依据方法选择 block，即使 history=true 也继续用 block 池；历史批量读取与实时区块读取竞争同一批供应商容量。
5. 分池不等于独立预算。多个池反复使用同样供应商；两个进程共用供应商预算。当前统一默认限额不能代表供应商承诺容量；备用竞速也消耗请求数。
6. 最新链头能力不能从固定旧块测试推断。本轮为公平比较固定到参考高度前 50 块；此前生产已出现节点落后 1 块、invalid block range，仍需单独处理节点同步差异。
7. dataseed 多域名及 PublicNode 两域名不能按域名数量计算独立容灾能力。官方两个 bnbchain dataseed 域名在当前程序中已共享预算；其他别名是否共享后台配额不能仅靠此次探测确定。

## 建议分工（尚未实施）

| 功能 | 建议主力 | 备用/约束 |
| --- | --- | --- |
| 实时日志 | 48.club + fast | PublicNode 按近期方法健康有条件备用；bloXroute 移出实时日志常规路径 |
| 可覆盖的近历史日志 | 48.club + fast 的剩余容量 | 与实时分别排队，给实时预留额度；按查询范围验证可用性 |
| 当前旧历史缺口 | 具备目标区间能力的独立历史日志服务 | 现有 bloXroute 可作隔离的低并发临时来源，但本轮 1/2 成功不能担当可靠唯一来源 |
| 高度/区块/交易回执 | Alchemy 公共入口 + OP | dataseed 补充；B 仅按方法健康降级备用；回执不能跟随区块健康一起判定 |
| 合约状态 | N/D/O 分担，A 提供低延迟容量 | 不把全部状态请求集中到单个最快公共入口 |
| WSS | 保留当前正常连接 | 增加不同供应商的订阅源才是真正跨供应商冗余 |

所有建议保持既有监控频率，包括 Factory 500 ms。优化应通过方法/范围路由、请求合并、优先级和历史任务隔离减少浪费。此次没有测供应商最大 RPS，不能给出“调成某个数就永不限流”的保证；稳定历史源需要以实际区间验收，历史日志服务与历史状态 archive 服务不是同一能力。
